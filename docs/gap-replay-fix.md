# 旧反馈重复生成缺口修复

日期：2026-10-24。分支：`codex/agentic-rag-next`。

## 问题与修改

旧回答先收到“没帮助”，后来标为“已解决”。两项选择会分别保留。原扫描器只要看到“没帮助”就继续派单；反馈更新时间超过 1 小时后，又能绕过去重窗口。

本次修改：

- 未解决判定先检查明确的解决状态，再兼容旧 `adopt` 字段。已解决不会因历史点踩再次进入扫描，帮助度评分仍保留。
- 显式反馈提交使用合并后的状态判定是否派单。晚到的自动收尾只初始化选择，不覆盖用户反馈。
- 强缺口保存来源回答、来源反馈和稳定来源键。反馈保存处理确认。来源键不包含更新时间，因此刷新反馈时间和进程重启不会重复派生同一来源。
- 合并来源先原子写入目标缺口。确认失败后，可从目标缺口查回原关联。
- 新建和合并共用 `gap_source_feedback_unique_v1` 唯一部分多键索引。旧记录和空数组不参与约束。索引无法建立时，扫描停止本轮写入。发生唯一冲突时，查询已有来源的目标，再确认处理结果。
- 已知上下文只在会话、产品和业务一致时合并。未知上下文保留既有的同题窗口兼容规则。
- 完成策略待办时，精确完成关联的 `strategy_pending` 缺口。重复完成请求可以补偿回写失败，不重复增加处理历史，也不覆盖知识候选的复核或发布状态。
- 对旧记录，扫描会核对相同回答的已完成待办。选择合并目标时，也会排除已完成绑定待办对应的旧策略缺口。新的回答再次失败，仍可登记。

业务模型默认序列化、HTTP 字段、审批状态、已有来源 ID 和内容摘要算法保持原有契约。新增来源字段只作为缺口存储的内部元数据。

## 生效与历史数据

重启使用本分支代码的查询服务后，新扫描规则生效。启动和扫描会检查来源唯一索引。若日志提示索引建立失败，应先处理索引权限或已有来源冲突，再恢复扫描。

本次没有自动删除或改写正式库的旧重复条目。旧条目缺少准确来源关系，不能仅凭问题文本批量删除。已有处理历史保留；这类条目需要单独核对后归档。

本次没有启动常驻测试服务。隔离测试数据和日志保留。未自动提交、推送或部署。
