第三步：切子块（split_section_children）

子块只取本章节自身的块，不含嵌套子章节的文本。否则同一段内容会在父章节与子章节各存一份。

打包规则（_pack_blocks + _merge_short_parts + _split_oversized）：

常量 默认 作用

CHUNK_OVERLAP 50 仅在「单个原子块必须切开」时生效
CHUNK_MIN 400 同章节内过短的块向后合并的门槛

贪心打包的逻辑：逐个追加原子块，累计超过 CHUNK_SIZE 就换段； 单个原子块长度落在 [CHUNK_SIZE, CHUNK_MAX_SIZE] 之间时不切——它本身已是语义完整的单元， 按字符切开只会制造纯重叠的碎片尾巴。超过 CHUNK_MAX_SIZE 才按分隔符切， 表格切分时复制表头与分隔行，代码块切分时补齐围栏。

设计取舍：长度口径一律按正文比较（不含标题前缀）。 子块最终形态是 f"{title}\n{body}"。若用「含标题前缀」的长度判断短块合并， 标题越长越容易误判，该步骤会退化甚至永不触发。口径统一为正文后， 阈值才和人的直觉一致。

入库分四步，顺序不可颠倒：

① 对齐 schema（_align_to_schema）

② 分批 upsert（_batch_upsert）

③ 对账条数

    fail("insert_count", f"对账失败：期望 {len(rows)} 条，实际写入 {written} 条")

④ 删除陈旧块（_delete_stale_chunks）

查同 file_title 下现有 ID，删掉本次未产出的那些（章节被删或改名时产生）。 查询失败只告警，绝不回退成「先删后插」——那会制造数据空窗。

设计取舍：为什么是「先写新后清旧」而不是「先清后写」。 一次导入要写三处存储（Milvus 子块、Mongo 父块、MinIO 图片），彼此没有事务。 「先删后插」在中途失败时会留下空库；「先写新后清旧」最坏结果是新旧并存， 而新数据已经可查。所有三处都遵循这个顺序：

存储 写法
Milvus upsert 新块 → 删同 file_title 下非新 ID
MongoDB parent_id upsert 新块 → 删 parent_id $nin new_ids 旧块
MinIO 上传新图 → remove_stale_images 清未引用旧图

父块写 Mongo 且失败不阻断：父块只用于补章节背景。写失败只记 error， 子块已在 Milvus 中可用，最坏结果是答案少了跨段落的上下文，不影响能否作答。

对账口径（reconcile_after_import，只读、只记日志、绝不阻断）：

对象 口径 理由
Milvus 子块 比对 chunk_id 集合，不是条数 按 file_title 计数会把上一次导入的旧块算进去，旧块数恰好等于期望值时「假通过」；集合比对直接回答「本次产出的每个 ID 是否可查」
MongoDB 父块 条数比较 Mongo 强一致读，口径明确
MinIO 图片 只输出对象计数，不判定 无法从 state 推出期望图片数（Markdown 里的引用才是权威），判定会误报

Milvus 对尚未 seal 的 growing segment 存在可见性延迟，刚 upsert 完立刻查可能稳定读到 0 行。 因此对账先重试，从第 2 次起先 flush 再重查，避免把延迟误报成「对账不符」。

② 本地优先（prefer_local_docs）

③ 联网条数上限：WEB_MAX_IN_CONTEXT（2），仅在本地有命中时生效。

④ 累计断崖截断（dyn_limit_reranker_docs）

设计取舍：用「累计」而不是「相邻」判断断崖。 相邻两条的分数波动很常见，用相邻差判断会把长尾里的相关文档误切。 以最高分为基准累计下跌，才反映「整体已经掉出相关区间」。

⑤ 权威条目保底（ensure_evolution_docs）：截断后把被切掉的进化条目前置补回。

全零命中时跳过重排直接返回，避免对空列表做无意义调用。

3.2 核心数据模型与存储方案

3.2.1 Milvus 三个集合

集合 主键 关键字段 向量 / metric
kb_chunks chunk_id VARCHAR(40) doc_id / parent_id / file_title / item_name / title / parent_title / heading_path / part(INT16) / seq / page / content / content_hash dense COSINE + sparse IP

索引：HNSW（M=64 / efConstruction=100），稀疏用 SPARSE_INVERTED_INDEX， dense 维度 1024（BGE-M3）。

为什么 kb_evolution_items 用 IP 而 kb_chunks 用 COSINE。 BGE-M3 稠密向量已 L2 归一化，IP 与 COSINE 排序等价，两种口径都正确。 关键是每个集合的 metric 必须与其建表时一致——不一致时 Milvus 会报 metric type not match 并静默返回 None，表现为「召回 0 条」。

3.4.3 可扩展性

当前明确是单进程形态，以下结构都在进程内存里：

  • SSE 通道与订阅者绑定
  • 任务进度（task_state）
  • 导入并发信号量
  • 主体目录缓存、参数注册表缓存
  • 调度器（无分布式锁）

因此多 worker 会出问题：丢流、进度错乱、调度重复扫描。 要水平扩展需要先把上述状态外移到 Redis（通道、进度、锁）， 并把调度器改成单实例选举。

另一个必须注意的点：Windows 允许两个进程绑定同一端口。 若 POST /api/query 与 GET /api/stream 被随机分发到不同进程，流式回答会卡住。 用 Get-NetTCPConnection -State Listen | Where-Object LocalPort -eq 8001 确认只有一行。

文件头魔数校验 PDF 必须是 %PDF-；md 拒绝含 \x00 且必须是 UTF-8

前端 XSS 防护 escapeHtml 统一转义；外链只接受 http(s)
静态资源白名单 /static/{asset} 只服务登记过的文件
PII 拦截 候选知识命中手机号 / 身份证 / 邮箱即拒绝
密钥不入库 .env 已在 .gitignore 中

两处鉴权的形态不同，容易混淆：

  • 导入读 settings.import_.admin_token，而 settings.py 给它带了一个硬编码的开发默认令牌。 「没配」也能跑通，生产部署必须覆盖。
  • 审批由 app/api/routers/evolution.py 直接读 os.getenv("EVOLUTION_ADMIN_TOKEN")，不走 settings。 未配置时写操作一律 503。

3.6.2 已知安全短板（客观陈述）

  • 无用户体系与登录态：会话仅靠前端生成的 session_id 区分，任何人猜到 ID 即可读取该会话历史。
  • 读接口无鉴权：/api/history、/api/query 等读操作不需要令牌。
  • CORS 默认 *：部署到公网必须显式收敛 CORS_ORIGINS。
  • 令牌是单一静态值：无轮换、无过期、无审计日志。
  • 导入令牌有硬编码默认值：若忘记覆盖，等于公开。

上生产前至少要补齐：用户登录与会话归属校验、读接口鉴权、CORS 收敛、令牌改为密钥管理服务下发。

3.7 设计权衡小结

3.7.1 值得称道的设计

  1. 确定性优先于模型推断。 主体消解的两条路径都把「意图」当作结构化字段直传， 而不是让模型从历史里猜。模型只在真正需要语义理解的地方出现。
  2. 契约显式化。 集合名、字段名、state 键名、SSE 事件名都被当作契约对待， 改动时能立刻判断爆炸半径。
  3. 无事务场景下的「先写新后清旧」。 三处存储统一这个顺序，最坏结果是新旧并存而非数据空窗。
  4. 降级边界统一。 增值能力（联网、HyDE、自进化、父块）失败一律降级为空，不阻断主链路； 硬依赖（rewritten_query）缺失才失败。
  5. 确定性 ID。 chunk_id 只编码结构，重复导入不重新分配，标注与引用长期有效。
  6. 同一判据复用在多处。 「无信息型答案」的判定在生成、审批、召回三处共用一份， 语义不漂移。

3.7.2 主要权衡与代价

权衡 代价
单进程换取实现简洁 无法水平扩展；多 worker 会丢流、重复调度
进程内存缓存换取低延迟 重启后缓存与进度丢失；多实例间不一致
先写新后清旧换取无空窗 需要额外的删除步骤与对账来发现残留
断崖截断换取上下文精简 参数不当会切掉长尾里的相关文档
本地优先换取权威性 本地命中质量差时会压制更准确的联网结果
反问兜底只看「最近一条」 不支持跨多轮的意图继承
候选成员判定从严 用户输入不在候选内的主体时退回模型改写

3.7.3 建议的改进方向（如需上生产）

优先级 方向
高 引入用户体系与会话归属校验；读接口加鉴权；CORS 收敛
高 把 SSE 通道、任务进度、调度锁外移到 Redis，支持多 worker
中 引入消息队列承载导入任务，支持跨进程并发控制与任务重放
中 主体消解引入更稳的指代消解，减少对「最近一条反问」的依赖
中 补充切分质量与检索质量的持续评测（app/rag_eval 已具备基础）
低 令牌改为密钥管理服务下发并支持轮换
