# 闲聊路由和缺口处理修复记录

日期：2026-10-23。分支：`codex/agentic-rag-architecture`。修复起点：`797d298`。

## 问题和原因

用户输入“你好”后，分类模型超过 2 秒，系统回退到产品问答。对运行记录的只读检查确认了 `intent_timeout`。该问候还留下了错误的未解决信号和强缺口。

另一条强缺口的类型为 `reading_miss`。调度器只为 `knowledge_missing` 生成知识候选，因此直接跳过该记录。跳过后没有策略修复待办，也没有重新处理持久化缺口。审批页只读取候选集合，无法展示缺口的处理原因。

后续截图中“烫金机有蓝牙吗”出现三张未解决问题卡片。只读检查确认：同一会话、同一 HAK 180 产品的两次失败回答分别产生“缺资料”登记，缺口扫描又产生“阅读遗漏”登记。原列表逐条展示，未按处理任务合并。

再次提问时，人工已将缺口标记为 `dismissed`，并完成原待办。新查询登记没有读取该忽略决定，因此仍新增一条待办。人工忽略与新查询、反馈、扫描之间缺少状态联动。

## 修复行为

- 纯问候和感谢按完整输入匹配，直接进入闲聊。混合产品问题仍进入产品问答。原开关和分类超时策略继续有效。
- 扫描时过滤历史纯寒暄信号。已产生的纯寒暄缺口保留原记录，并在后台处理时标记为已忽略。
- 后台从数据库读取未处理强缺口。检索、阅读和生成问题进入策略待办。明确的知识缺失继续使用知识候选流程。
- 审批页新增“缺口处理”，显示类型、状态和原因。未处理记录优先显示，避免被近期已处理记录挡住。
- 管理员核对资料并填写原因后，可以将不确定缺口确认为知识缺失。系统登记空答案、空来源的 `need_info` 候选，等待人工补充。
- 候选编辑表单可填写来源分块和产品。文档来源继续执行版本及答案支持校验。人工补充允许来源分块留空，经管理员保存和审批后直接入库。
- 后台创建候选或待办前，原子领取缺口并保存租约。处理期间不接受并发忽略或改类。租约到期后可恢复。
- 写入前后检查领取者及租约。新候选和待办先登记为内部 `staged` 状态，缺口绑定成功后才变为 `ready`。暂存记录不展示、不计入候选数，不能审批或召回，也不参与问题去重。
- 缺口绑定后若进程中断，下轮调度会恢复登记。失效任务在写入期间留下的孤立暂存记录保留审计，不会出现在审批页。
- 自动和人工路径共用候选主键。重试复用已存在的候选，不覆盖人工编辑或审批结果。队列按上次尝试时间轮转，持续失败的旧记录不会挡住后续记录。
- 未解决问题按会话、已确认产品、业务和规范化问题合并展示。保留原始登记。整组保存时保留各成员此前的处理信息。页面显示原因、关联登记数及历史，并默认只显示未完成项。
- 已完成待办只读，防止旧页面覆盖已完成结果。后续新失败另行登记。无法恢复产品上下文的旧登记不合并。
- 人工忽略决定统一作用于同会话、同产品、同业务和同题的自动登记。新失败信号继续保留，后台不再生成重复缺口；已排队同题记录停止处理。普通完成状态继续允许报告后续真实失败。
- 读取侧将已有重复待办显示为“已忽略”，保留原始登记和已完成历史。页面增加已忽略筛选及原因说明。服务器业务标签贯穿反馈、缺口和待办，客户端标签不能覆盖已保存回答。

## 运行步骤

1. 重启查询服务，刷新审批页。
2. 输入“你好”，确认进入闲聊。纯问候不消耗分类模型调用，闲聊作答仍使用现有回答模型。
3. 在“缺口处理”查看旧记录。下轮调度会恢复未处理记录。
4. 对产品缺口先核对原资料。确认缺失后，填写原因并登记待补充候选。
5. 补充已核实的答案和产品，保存后确认入库。人工补充可留空来源分块；有文档依据时填写实际分块 ID。
