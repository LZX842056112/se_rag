# 知识治理操作说明

查询证据、用户反馈和候选答案具有不同用途。用户反馈不能作为事实来源。模型输出的来源 ID 必须通过服务端校验。

缺口有四类。`retrieval_miss` 表示检索遗漏。`reading_miss` 表示阅读遗漏。`generation_error` 表示生成错误。`knowledge_missing` 表示知识缺失。只有最后一类进入 FAQ 生成。没有明确的知识缺失证据时，默认归入检索遗漏。

审批页的“缺口处理”区显示缺口类型、状态和处理原因。检索、阅读和生成问题会进入“未解决问题”待办，缺口状态为 `strategy_pending`。它们不再只记录为跳过。后台每轮会读取持久化的未处理强缺口，因此修复前已扫描的记录也会恢复处理。

管理员核对原资料后，可以填写原因并点击“确认为知识缺失”。系统先保存复核状态，再幂等登记 `need_info` 候选。候选答案和来源为空，不调用模型编造事实。中途失败时，后台从 `reviewing` 状态继续处理。重复确认不会增加第二条候选。管理员也可填写原因并忽略误报。

人工忽略决定会作用于本会话同一产品、业务和问题的后续自动登记。查询登记、显式反馈和缺口扫描使用同一范围判断。已排队的重复缺口记录原忽略缺口 ID，并停止自动生成候选。原始失败信号继续保留；人工忽略不计作答案已解决，也不改变知识库。页面将已有的同题未完成待办显示为“已忽略”，已完成历史继续保留。业务标签在服务器的回答、反馈、缺口和待办之间传递，避免不同业务相互抑制。

后台任务先领取缺口，再生成候选或策略待办。领取信息包含持有者和租约。写入前后必须检查租约。新登记先保存为内部 `staged` 状态，缺口成功绑定后再转为 `ready`。暂存候选不展示、不计数，不能审批或召回，也不参与问题去重。若缺口绑定后进程中断，后续调度会恢复登记。失效任务留下的孤立暂存记录保留审计，不进入审批流程。

在候选卡片点击“编辑”，补充已核实的事实答案和产品名称。人工补充时，来源分块 ID 可以留空。保存后显示“人工补充”，再点击“确认并入库”，发布到 `kb_evolution_items`。填写文档来源时，保存仍校验产品和版本，审批仍检查原文支持关系。GET `/api/evolution/gaps` 和 POST `/api/evolution/gaps/{gap_id}/review` 都要求管理令牌。

历史纯寒暄信号不再产生缺口。修复前已产生的纯寒暄强缺口会标记为 `dismissed`，保留原记录和原因。此操作在下轮后台调度执行，不删除反馈或历史消息。

自动生成的候选必须记录实际读取的分块 ID。生成器只能选择本轮上下文中的 ID。服务端重新读取原文，并检查产品、文档版本、有效期和正文摘要。模型不能提供权威的版本字段，也不能自行标记为人工知识。

审批保留现有 `(bool, message)` 返回格式。外部状态继续使用 `draft`、`active`、`deprecated` 等值。内部 `publication_status` 表示发布进度。只有内部和外部状态都为 `active` 的条目可以召回。未迁移的旧条目不能召回。

文档来源候选在审批时检查答案支持关系。原文包含完整答案时，检查直接通过。其它答案调用接地性检查器。评分必须有限，且不小于 `EVOLUTION_GROUNDEDNESS_MIN`。无法评分时，拒绝发布。检查器使用完整来源正文。

人工补充可调用 `approval.service.edit(..., source_refs=[], item_names=[...])`，或继续使用原有仅传答案的编辑调用。管理员保存无文档来源的答案后，系统记录 `knowledge_origin=manual` 和服务器编辑时间。审批记录批准时间及本版内容指纹。未编辑确认、未审批或指纹不匹配的人工条目不能发布或召回。问题、产品和事实答案仍不能为空。

人工补充的来源分块与来源版本为空，不依赖手册分块。已有文档条目的内容指纹保持兼容。管理员填写来源分块后，条目改回文档校验并绑定原文版本。编辑已发布内容会先撤回旧内容，并清除旧审批。再次审批后，系统发布新版本。旧的无来源条目不会自动获得信任，须人工编辑和审批。

发布任务存入候选集合对应的 `_publication_tasks` 集合。任务主键包含候选 ID、内容版本、内容摘要和索引版本。Mongo 主键保证任务唯一。任务有 120 秒租约。索引写入使用确定性 ID。失败后，任务保留错误原因和重试次数。重试间隔按指数增加，上限为一小时。进程重启后，工作线程可以领取租约已到期的任务。

后台循环调用 `run_publication_tasks()`。运维程序也可以调用此函数。重复审批会继续处理同一发布任务。索引完成前，候选保持不可召回。向量 ID 包含发布版本，不覆盖其它版本的 ID。

撤回先修改 Mongo 状态，再删除索引。删除失败时，持久化任务继续重试。召回在返回结果前读取 Mongo，检查人工审批指纹或重新校验文档来源。索引中残留的旧向量不能绕过这个检查。Mongo 不可用时，FAQ 召回返回空结果。文档原文不可用时，其派生 FAQ 不能召回。

替换或删除源文档前，调用 `invalidate_document(doc_id, version=None)`。省略版本时，系统撤回该文档的全部派生 FAQ。指定版本时，系统只撤回依赖该旧版本的 FAQ。导入程序必须在写入新正文前调用此接口。写入开关关闭时，接口不修改数据。

迁移默认只报告。运行 `python -m app.evolution.governance` 查看数量。运行 `python -m app.evolution.governance --apply` 添加治理字段。迁移不删除候选，也不修改外部状态。所有旧记录进入 `review_required`。迁移不会自动信任旧答案或旧来源。

`recall_enabled()` 控制 FAQ 读取。`writes_enabled()` 控制后台知识写入。未配置独立开关时，两者使用旧的 `evolution.enabled`。离线评测应关闭写入，并使用隔离资源。调用 `approved_faq_snapshot()` 保存已发布内容摘要、内容版本、索引版本和来源版本。比较实验必须使用同一份快照。

本实现没有增加图索引或句子索引。当前发布目标是现有 FAQ 向量索引。后续增加索引时，必须扩展发布任务，并在全部目标完成后激活候选。
