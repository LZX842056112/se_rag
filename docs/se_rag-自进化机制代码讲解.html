导读与结论

结论
这套「自进化」= 知识回流 + 检索参数微调，不训练模型、不改权重。

它把「用户答不出来」这个现象，转化为一条结构化知识（FAQ），经人工审批后写入独立的 Milvus 集合， 在后续查询中作为第三路召回参与 RRF 融合；同时用反馈指标小幅调整三个检索参数。 所谓「进化」，本质是数据与配置的迭代，不是模型参数的迭代。 这一点在 docs/se_rag-技术讲解文档.md:47 有明确表述。

注意
「自进化」这个词容易误导。

代码里没有任何训练、微调、梯度更新。整个机制的可变部分只有三样： Milvus 里的 FAQ 条目、Mongo 里的候选与缺口状态、param_registry 里的 3 个整数。 理解这一点，后面所有「为什么这里要人工审批」「为什么回测只是聚合统计」就都顺了。

01

整体架构与模块划分

1.1一句话定位

app/evolution/ 是一个与主问答链路弱耦合的旁路系统。 它只通过四个接触点与主链路相连：读侧召回（search_evolution_items）、 写侧信号（flush_session_signals）、RRF 融合（fuse_by_rrf）、 以及参数读取（param_registry.get_param）。 其余部分——扫描、分级、生成、审批、回测——全部在独立调度循环或独立 HTTP 路由中完成。

设计
这个隔离是刻意的。

所有对外函数都做了 try/except 兜底并返回空值：search_evolution_items 异常返回 []（ retrieval.py:114-116）、run_scan_and_generate_once 异常只记日志（ scheduler.py:73-74）、compute_groundedness 失败返回 None（ grounding.py:38-41）。自进化挂掉不会让问答挂掉，这是读这套代码的第一条主线。

辨析
k_gaps 与 query_issues 是两套东西，不要混。

k_gaps（缺口）是进化流水线的工作队列，只有 strong 级才落库，它的下游是 LLM 生成候选。 query_issues（待办）是人工客服的工作队列，由 issues.register_unresolved 在 pipeline.py:55 写入，带负责人与处理结果字段。 两者由同一条反馈触发，但服务对象不同：前者给机器，后者给人。

1.4闭环的双向数据流

自进化之所以叫「闭环」，是因为它同时消费和产出问答链路的输入输出。 把它拆成写侧（问答 → 反馈）和读侧（进化 → 问答）两条流，环路才看得清。

两条数据流的对接点：写侧终点是 fb_events，读侧起点是 kb_evolution_items
方向流经模块数据形态变化
写侧 pipeline → collector → detector → generator → approval 原始回答 + 引用 → FeedbackEvent（扁平） → KnowledgeGap（带加权分） → KnowledgeCandidate（FAQ 文本） → active 状态 + evo_doc_id

3.6回测止损算法：四分支判定

「回测」这个词容易误解。它不是重新跑一套标注问答集，而是把观察窗内的历史反馈按条目聚合， 算出每条进化知识的命中数、采纳率、拒绝率，再据此决定去留。

先建倒排索引，避免 N+1

一次游标遍历 fb_events，按每个 cited_chunk_id 把事件塞进对应桶。 之后每个候选只需 buckets.get(evo_id) 一次查表。 投影只取 4 个字段，减少网络传输。这个写法值得单独记：候选数量增长时，朴素实现会变成 O(N×M)。

四分支判定（顺序不可调换）

顺序条件verdict设计意图
①hits == 0hold从没被引用过。可能是还没被问到，不能判死
②hits < backtest_min_hits（默认 3）hold防单条差评误杀。人工审批过的知识，至少要 3 次证据才下结论
③reject_rate > reject_rate_max（默认 0.30）remove拒绝率超标。先于采纳率判断——即使采纳率也达标，只要拒绝率超限就下架
④adopt_rate ≥ attain_rate_min（默认 0.60）promote达标。但没有任何写操作——见下方警告
⑤其余（被引用但多为中立）hold继续观察，避免误杀
顺序
③ 在 ④ 之前，这个顺序有实际后果。

假设某条目被引用 50 次：30 次采纳、20 次拒绝。则 adopt_rate = 0.60（刚好达标）、 reject_rate = 0.40（超限）。因为 ③ 先判，结果是 remove 而非 promote。 如果调换顺序，这条知识就会被「晋级」而不是下架。改动这段代码时必须意识到这个优先级。

偏差
promote 是一个空动作。

result.verdict = "promote" 之后没有任何写操作，函数继续 results.append(result) 就结束了。 scheduler.run_backtest_once 也只统计 verdict == "remove" 的数量（scheduler.py:106）。 所以「晋级」在系统里没有任何实际效果，既不提升权重，也不改变状态，连日志都不打。 详见 §6 偏差 2。

向量化文本的构成

要害
只有 faq_answer 进向量，faq_question 不进。

这是个容易忽略的设计。检索时用户的 query 向量要与「主体 + 答案」比对，而不是与「问题」比对。 好处是：即使问法差异很大，只要答案内容相关就能召回。 代价是：如果答案写得很抽象、而问题很具体，召回可能失败。 这也是为什么 §3.3 里「入库了却召不回」仍然可能发生——强制并入只能救「已召回但被挤掉」的情况。

为什么重排还要再保一次

rerank_service.py:126-141 的 ensure_evolution_docs 在重排结果被截断到 RERANK_TOP_K 之后，把落选的进化条目补回。这是第二道保底： RRF 保底保证了「进候选集」，重排保底保证了「进最终上下文」。 两道保底叠在一起，说明这条链路的设计者遇到过「知识明明入库了，客服还是答不出」的问题， 并且在两个可能丢失的位置都打了补丁。

副作用
保底席位的代价是：进化条目可能挤占本应属于 kb 权威文档的位置。 如果进化条目质量不高，会拉低整体答案质量——这正是回测止损存在的理由。 两者是一组对抗关系：保底让知识「一定能进」，回测让坏知识「尽快出」。

实现偏差审计

以下 8 条是逐行核对代码与注释/文档后确认的偏差。每条都给出可复现的代码证据、实际影响与修复方向。 它们不影响「闭环能跑通」这个结论，但直接影响对系统能力的判断——尤其第 1 条，会改变你对「分级」这一设计的理解。

D1缺口分级退化为常量，weak / none 与 pending 全部不可达

证据　detector.py:3 的模块 docstring 写「仅 strong 缺口进入候选生成；weak/none 归档 k_gaps 后结束」，但 detector.py:126-129 只在 gap.status == "candidate" 时 insert。更关键的是 detector.py:110-114 的查询条件 $or: [{adopt: False}, {thumbs: {$lt: 0}}] 与 detector.py:73 的 user_bad 定义完全等价，因此被扫到的每条事件 signals.user 恒为 1.0。

影响　confidence 在默认权重下恒为 0.7，恒判 strong。gap_weak_threshold 是死配置；status="pending" 永不写入；_is_duplicated 的 pending 分支（detector.py:47）永不命中；「只有 strong 才生成候选」这道闸门实际不筛任何东西。

修复　两条路：① 让扫描条件宽于 user_bad（例如把「零命中但用户未评价」也纳入），恢复分级意义；② 引入连续信号替代布尔组合——检索最高相似度分、同 query 重复次数、groundedness 实际值。

D2promote 判定没有任何副作用

证据　runner.py:76-77 只执行 result.verdict = "promote"，之后没有写库、没有调权重、没有日志。整个函数唯一的写操作在 remove 分支（runner.py:81-90）。scheduler.py:106 也只统计 verdict == "remove"。

影响　回测闭环只有「下架」没有「晋级」。表现好的知识不会获得更高权重、更快通道或任何标记。promote 是一个只存在于返回值里的结论。

修复　至少落库 k_metrics 或在候选上写 promoted_at；若要影响检索，可让 rrf_weight 按条目分档（需扩展 Milvus schema 增加 weight 字段）。

D3MetricSnapshot 中四个字段永远是默认值

证据　models.py:78-80 定义 recall_k / precision / groundedness，但 metrics.py:16-29 的 compute_snapshot 只给 adopt_rate / gap_rate / params_snapshot 赋值。全仓搜索 recall_k 仅命中 models.py:78 一处。

影响　k_metrics 里这三个字段恒为 0.0。任何基于它们做的看板或告警都会显示 0。真正的 groundedness 在 answer_service.py:133 单独计算并写入 chat_message，与 k_metrics 完全无关。

修复　要么在 compute_snapshot 里聚合 chat_message.groundedness 填进去，要么从模型中删除这三个字段，避免误导。

D4两项配置无任何消费者

证据　groundedness_min（settings.py:315）与 gray_enabled（settings.py:316）在全仓搜索只命中 settings 定义处，无任何读取点。

影响　运维若通过改这两项来「调高可信度门槛」或「开启灰度」，不会有任何效果，也不会有任何提示。这是最危险的一类死配置：看起来能用。

修复　删除，或在启动时打印警告。若确实需要灰度，应实现为「按流量比例决定是否召回进化条目」。

D5调度进度与扫描游标是进程内变量，多 worker 会重复执行

证据　scheduler.py:27-28 的 _LAST_METRIC_TS / _LAST_BACKTEST_TS、detector.py:23 的 _CURSOR、param_registry.py:14 的 _CACHE 全部是模块级变量。

影响　多进程部署时每个进程各有一份游标，会重复扫描同一批 fb_events、重复生成候选（去重窗口能挡住大部分，但不是全部）、重复跑回测。SingleWorkerLease（query_server.py:31）是唯一防线，属于部署约束而非代码保证。

修复　把游标写入 Mongo（例如 param_registry 加一个 _cursor 键），或用 Redis 分布式锁包住 run_evolution_cycle_once。docs/superpowers/plans/2026-10-18-internal-trial.md:15 已把它列为扩容前置工作。

D6reject 不校验状态，也不下架向量

证据　service.py:106-118 无条件执行 update_one({"_id": oid}, {"$set": {"status": "rejected"}})，既没有检查当前状态，也没有调用 deactivate。

影响　对一条 active 的候选调用 reject，会出现状态与存储不一致：Mongo 说 rejected，Milvus 里的向量仍在且 status 字段仍是 active，因此仍会被召回。要等到下一次回测（默认 24 小时）才可能被 remove，而回测只看 k_candidates 中 status="active" 的条目——该候选已不在其中，所以永远不会被回测清理。这是一条真正的泄漏路径。

修复　reject 前读状态，若为 active 则先 deactivate(evo_doc_id) 再改状态；或直接拒绝「对 active 候选执行 reject」，引导用户改用 DELETE（remove_candidate 会正确下架）。

D7审批回滚会清空 reason

证据　service.py:87 回滚语句为 {"$set": {"status": "draft", "evo_doc_id": None, "reason": ""}}，把管理员刚填的审批理由覆盖成空串。

影响　Milvus 写入失败时，管理员填写的理由丢失，回滚后的候选看起来像从未被处理过。排查「为什么这条没入库」时缺少线索。

修复　回滚时保留 reason，改为 {"$set": {"status": "draft", "evo_doc_id": None}}，或写入一个 last_error 字段。

D8Mongo 与 Milvus 之间没有共同事务，崩溃窗口未消除

证据　service.py:67-92 的顺序是：Mongo 抢占为 active → Milvus upsert → 成功则回写缺口。两个存储各自独立提交。

影响　三个崩溃窗口：① 抢占后、upsert 前崩溃 → Mongo 有 evo_doc_id 但 Milvus 无条目，检索永远查不到；② upsert 后、_mark_gap 前崩溃 → 候选正常但缺口停在 candidate；③ upsert 成功但返回时网络异常 → 走进回滚分支，Mongo 回到 draft 而 Milvus 已写入，形成孤儿向量。

修复　把回滚改为「幂等重试 + 对账」而非「直接回滚」：先 deactivate 再回滚 Mongo；另外加一个周期性对账任务，扫描 k_candidates 中 active 但 Milvus 查不到的条目。

小结
这 8 条的共性：都是「静默」的。

没有一条会抛异常、打错误日志或让接口报错。D1 让分级失去意义、D2 让晋级成为空话、D3/D4 让配置与指标显示假值、D5 让多 worker 重复劳动、D6 让知识泄漏、D7 让排查线索消失、D8 留下孤儿数据。 它们不影响系统跑通，但影响你对系统能力的准确判断——这也是读代码比读文档更可靠的原因。
